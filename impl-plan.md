## Scope and assumptions

- The approved product baseline includes create, view/inspect, edit, permanent deletion, completion/pending, optional priority and due date, persistence, filters, ordering, validation, and errors. **This implementation authorization covers only the unblocked slices:** create, view/inspect, permanent delete after confirmation, optional priority/due date on create, persistence, list filters/ordering, and current-state display. Edit and completion/pending writes are not implemented while Q9 remains open.
- No authentication, roles, multi-user collaboration, cloud deployment, reminders, notifications, attachments, or separate audit history are implemented.
- Current desktop Chrome is the initial compatibility target. Q7 quality targets and additional browser/mobile support remain unresolved; do not claim them or invent measurable thresholds.
- Honor approved validation at the authoritative service/API boundary: trim title and optional description; title 1–100 characters after trimming; description no more than 1,000 characters after trimming; priority Low/Medium/High with Medium default; optional valid calendar date in exact `YYYY-MM-DD`, date-only with no timezone conversion and past dates allowed; new tasks incomplete. Invalid API input returns HTTP 400 with a clear message. Missing task read/edit/delete returns HTTP 404 with `Task not found`.
- Honor permanent deletion only after UI confirmation; do not introduce soft deletion or undo. Keep task data local and preserve it across normal restarts. Do not claim secure erasure, backup/recovery, or formal retention guarantees (Q8 remains open).
- Preserve the DR-001 design direction: serve UI and API from one intended same origin; bind the API to loopback, reject unexpected `Host` and browser `Origin`, do not enable permissive CORS, and protect mutations with origin checks and an appropriate JSON request. Include focused origin/host rejection and allowed-origin tests and direct API mutation tests. No authentication or roles are added.
- **Approved stack:** React + Vite (JavaScript), Node.js + Express, SQLite, and Vitest, selected by the user on 2026-10-22. Approved TASK-001 contracts are recorded in `architecture.md`: create/list/read/delete routes and response statuses/envelopes; UUID v4 IDs; Unicode code-point counting; `%LOCALAPPDATA%\ToDoApplication\data.sqlite` with absolute `TODO_DB_PATH` override and transactional versioned migrations; UTC ISO-8601 millisecond creation timestamps; duplicate titles allowed; no pagination; list/detail fields; empty description `""`; “No tasks yet” and “Task created” feedback; unknown create fields return HTTP 400. Do not change these decisions without approval.
- Illustrative paths in the task table (for example `client/`, `server/`, `tests/`) are proposed locations, not existing files. Final layout follows the human-approved toolchain and repository conventions.
- Do not invent Q9 policies. In particular, affected edit/completion work stays blocked until the human decides or explicitly excludes: (1) which fields can be edited, (2) whether updates are partial or full, (3) update-conflict behavior, and (4) completion write shape and any timestamp/side effects. The related question of independent priority/due-date edits must also be settled or explicitly excluded before implementing that flow. The remaining Q9 items may be explicitly excluded from MVP implementation without inventing behavior; document those exclusions.

## Test and quality strategy

- **Contract-first direct API testing:** Exercise API endpoints without UI to prove validation, defaults, filtering/order, persistence, lifecycle, errors, and origin protections. Keep direct API validation tests distinct from UI validation tests.
- **Validation boundaries:** Test title/description trimming and length edges; invalid/missing fields; priority enum/default; exact date format, impossible calendar dates, leap dates, past dates, and date-only round trip. Confirm invalid API requests return HTTP 400 and clear messages, and that client validation cannot bypass server checks.
- **Lifecycle and list behavior:** Test incomplete default, complete/pending only if Q9 completion contract is approved, All/Pending/Completed membership, newest-created-first ordering, missing-item `Task not found`/404 for read and applicable writes, permanent deletion after UI confirmation, cancellation without mutation, and post-delete absence.
- **Security/origin:** Focused positive and negative tests for intended origin and rejected origins/hosts; mutation tests against cross-origin, missing/unexpected Origin, and inappropriate content type according to approved implementation details; verify no permissive CORS and loopback-only binding. No role/authorization tests are applicable to the approved no-auth, single-user MVP.
- **Privacy and errors:** Assert task descriptions and unnecessary task content do not appear in logs or API error responses; assert internal exceptions/paths/SQL do not leak. Keep logs local and no remote telemetry.
- **Persistence/consistency:** Verify persistence across restart, transactional atomicity on failed mutations, parameterized database operations, and concurrent independent writes. Test same-task update conflicts only after Q9 conflict semantics are decided; do not encode a winner policy before then.
- **UI/integration:** Verify filter and confirmation interactions, error display, and integrated browser behavior in current desktop Chrome. Use deterministic fixtures and clean test data. No invented accessibility/performance thresholds.
- **Tooling/quality gates:** After approved stack selection, use its actual formatter/linter, automated tests, and production build. Record commands, environment, and results. Add CI only if explicitly included/approved. No test, build, lint, or CI check is claimed executed by this planning artifact.
